How this is measured

  • Components, attributes and properties come from the JavaScript core's schema (@doenet/static-assets) and the Rust core's own inventory (cargo run --example component_inventory). Names are compared case-insensitively. Elements the parser rewrites, such as <section> into <division type="section">, count as the Rust component they become.
  • Complete means Rust has the component and every one of its JavaScript attributes and public properties. name, extend and copy count as supported on every Rust component, because the Rust core handles them while building the document.
  • Properties in green are public in Rust (referenceable as $c.prop); amber ones exist in Rust but are private, which is enough for tests but not for authors.
  • A supported name is not proof of the same behavior. The test suite is the behavioral check: it runs every worker test with DOENET_TEST_CORE=rust, and each failure is classified by its first error. A test that reads a missing state variable names it; a wrong value is an AssertionError.
  • Uses in tests counts tags and attributes in the DoenetML of the worker's test files. It is approximate and only meant to rank what to port first.
  • The Rust core ignores attributes it doesn't know rather than rejecting them, so an unsupported attribute usually shows up as a wrong value, not as a named gap.
