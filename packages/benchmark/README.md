# @doenet/benchmark

The performance suite: how the JS core, the Rust core and the cells core
compare on update time, load time, memory, state storage size and bundle
size. `PLAN.md` records the decisions; this file is how to use it.

It is a decision suite, re-run as the cores change, with raw results
committed. It is not a regression gate: timings carry product budgets as
reference lines, and only bundle size fails anything.

## The corpus

One manifest per fixture in `fixtures/*.json`. `npm run fixtures` lists them
and checks that each resolves to text.

| Field | Meaning |
|---|---|
| `name` | The file name without `.json`. Synthetic shapes are `shape-N`. |
| `tier` | `real` (a document an author would write) or `synthetic` (one mechanism at three sizes). |
| `mechanism` | What the fixture exercises, one line. |
| `source` | Where the DoenetML comes from: `{"file": "x.doenet"}` in `fixtures/`, `{"path": "..."}` relative to the repository root, or `{"generate": "shape-N"}` for `src/generate.mjs` (output cached in `fixtures/generated/`, ignored by git). |
| `steps` | The interaction script. The driver cycles through it and times every step; consecutive steps alternate values so each one changes something. |
| `structural` | The structural change, in the same form, or `null`. A structural step rebuilds the document (a repeat's length, a conditional's case). |
| `notes` | Anything a reader of the table needs to know. |

A step is `{"action", "target", ...}`. `target` is a name path as the
document resolves it (`p3.mi`). Actions, with the core action they map to:

| Action | Fields | Core action |
|---|---|---|
| `movePoint` | `x`, `y` | `movePoint` |
| `updateValue` | `value` | `updateRawValue` then `updateValue` on a math or text input |
| `submitAnswer` | | `submitAnswer` on an answer |
| `triggerActions` | | `triggerActions` on a triggerSet |

The synthetic shapes are generated by `src/generate.mjs` in the DoenetML
every core reads: `<mathInput>` for inputs and `<number>` for numeric
dependency. A `<math>` chain is one symbolic expression in every core and
measures something else, so only `symchain` uses `<math>`.

### Real documents

| Fixture | What it is |
|---|---|
| `homework` | Twelve calculus problems with math inputs, answers, hints and feedback. The reference document for the load and storage budgets. Written for the suite. |
| `lesson` | Prose: sections of text and math with one graph and two inline exercises, what PreTeXt embeds. Written for the suite; stands in for the PreTeXt sample article, which is PreTeXt XML, not DoenetML. |
| `sir` | The SIR simulation: function iterates feeding polylines and a table, with parameters bound to inputs. |
| `venn` | The JS core's memory-bench document: shaded Venn regions behind toggles, eight answers. |
| `adventure-500` | A three-way conditional over graphs of 500 points each, chosen by an input. Generated. |

### Synthetic shapes

`chain`, `fanout` and `repeat` at 100, 1,000 and 10,000; `symchain` and
`answers` at 10, 100 and 1,000. Plus the Rust core's two benchmark
documents, `rust-thousand-chain` and `rust-thousand-star`, so it has rows it
can run.

## The Node driver

```bash
npm run node -- --cores=javascript,rust,cells --fixtures=homework,chain-100
```

`src/run.mjs` runs every (core, fixture) in its own process with a 60 s
budget and appends one JSON line per measurement to
`results/raw/node-<date>.jsonl`. The process is `src/measure-one.ts` under
vite-node from `packages/doenetml-worker-javascript`, whose test utilities
give the three cores one interface (`DOENET_TEST_CORE` selects the core;
the Rust and cells adapters are `test-core-rust.ts` and
`test-core-cells.ts` there).

| Field | Meaning |
|---|---|
| `status` | `ok`; `unsupported` (the adapter refused the document or an action: a gap, not a failure); `timeout` with the `stage` reached (`parse`, `load`, `errors`, `steps`, `structural`); `error`. |
| `parse_ms` | DoenetML text to normalized DAST, by `@doenet/parser` alone. |
| `load_ms` | `createTestCore` on the text: parse, core construction and the first state. Includes the parse, so `load_ms - parse_ms` is the core's own share. |
| `heap_bytes` | JS heap growth across the load after a forced GC on each side. |
| `wasm_bytes` | Wasm linear memory after the load. The JS core's figure is the Rust binding its worker holds for DAST normalization. |
| `error_components` | Error components in the loaded document, where the core can report them (`null` otherwise). A document with errors is not a valid measurement. |
| `state_bytes`, `state_gzip_bytes` | The session's saved state after the steps, raw and gzipped. The cells core's is `save_state()` JSON: one `[scope, slot, kind, value]` entry per essential cell that differs from its default (`cells-core/src/document/state.rs`). The JS core's is the `coreState` string of its persistence payload. |
| `state_envelope_bytes` | JS core only: the whole persistence payload a host stores, `coreInfo` included. |
| `steps`, `structural` | Per step label, `n` samples and `p50_ms`, `p90_ms`, `max_ms`. Steps cycle for 20 rounds or 20 s, structural steps for 10 rounds. |

Each run is one vite-node process, which costs about ten seconds of
startup per measurement; that is harness overhead and appears only in
`wall_ms`.

## Reference budgets

| Measurement | Budget |
|---|---|
| Interactive tick, browser frame latency | 16 ms |
| Structural tick, browser | 50 ms |
| Load, text to first render, `homework` | 100 ms |
| Memory, marginal per viewer on a page | 20 MB |
| State storage, `homework` after the script | 2 KB raw |
| Bundle, brotli, everything a page fetches | 1 MB |
