# @doenet/benchmark

The performance suite: how the JS core, the Rust core and the cells core
compare on update time, load time, memory, state storage size and bundle
size. `PLAN.md` records the decisions; this file is how to use it.

It is a decision suite, re-run as the cores change, with raw results
committed as JSON under `results/raw/` (one array of records per run) and
rendered into `results/RESULTS.md`. It is not a regression gate: timings carry product budgets as
reference lines, and only bundle size fails anything.

## The corpus

One manifest per fixture in `fixtures/*.json`. `npm run fixtures` lists them
and checks that each resolves to text.

| Field | Meaning |
|---|---|
| `name` | The file name without `.json`. Synthetic shapes are `shape-N`. |
| `tier` | `real` (a document an author would write) or `synthetic` (one mechanism at three sizes). |
| `mechanism` | What the fixture exercises, one line. |
| `source` | Where the DoenetML comes from: `{"file": "x.doenet"}` in `fixtures/`, `{"path": "..."}` relative to the repository root, or `{"generate": "shape-N"}` for `src/generate.mjs` (output cached in `fixtures/generated/`, ignored by git). |
| `steps` | The interaction script. The driver cycles through it and times every step; consecutive steps alternate values so each one changes something. |
| `structural` | The structural change, in the same form, or `null`. A structural step rebuilds the document (a repeat's length, a conditional's case). |
| `notes` | Anything a reader of the table needs to know. |

A step is `{"action", "target", ...}`. `target` is a name path as the
document resolves it (`p3.mi`). Actions, with the core action they map to:

| Action | Fields | Core action |
|---|---|---|
| `movePoint` | `x`, `y` | `movePoint` |
| `updateValue` | `value`, `kind` (`"text"` for a text input; a math input otherwise) | `updateRawValue` (math) or `updateImmediateValue` (text), then `updateValue` |
| `submitAnswer` | | `submitAnswer` on an answer |
| `triggerActions` | | `triggerActions` on a triggerSet |

The synthetic shapes are generated by `src/generate.mjs` in the DoenetML
every core reads: `<mathInput>` for inputs and `<number>` for numeric
dependency. A `<math>` chain is one symbolic expression in every core and
measures something else, so only `symchain` uses `<math>`.

### Real documents

| Fixture | What it is |
|---|---|
| `homework` | Twelve calculus problems with math inputs, answers, hints and feedback. The reference document for the load and storage budgets. Written for the suite. |
| `lesson` | Prose: sections of text and math with one graph and two inline exercises, what PreTeXt embeds. Written for the suite; stands in for the PreTeXt sample article, which is PreTeXt XML, not DoenetML. |
| `sir` | The SIR simulation: function iterates feeding polylines and a table, with parameters bound to inputs. |
| `venn` | The JS core's memory-bench document: shaded Venn regions behind toggles, eight answers. |
| `adventure-500` | A three-way conditional over graphs of 500 points each, chosen by an input. Generated. |

### Synthetic shapes

`points`, `chain`, `fanout` and `repeat` at 100, 1,000 and 10,000;
`symchain` and `answers` at 10, 100 and 1,000. `points` is the one shape
every core runs. Plus the Rust core's two benchmark
documents, `rust-thousand-chain` and `rust-thousand-star`, so it has rows it
can run.

## The Node driver

```bash
npm run node -- --cores=javascript,rust,cells --fixtures=homework,chain-100
```

### Building the Rust core for a measurement

The workspace builds the Rust core's wasm with `wasm-pack --dev` and its
logging features, the build the JS core's worker ships for DAST
normalization: unoptimized, five to ten times slower than an optimized
build. The cells core is measured as a release build, so measure the Rust
core optimized too. Its release profile does not compile for wasm today
(`lib-doenetml-core`'s browser tests import a module gated on debug
assertions), so build the dev profile at opt-level 3, without the logging
features, then rebuild the bundles that carry it:

```bash
cd packages/doenetml-worker-rust
CARGO_PROFILE_DEV_OPT_LEVEL=3 npx wasm-pack build lib-js-wasm-binding --target web --dev
npx vite build && (cd ../doenetml-worker && npx vite build)
```

`src/run.mjs` runs every (core, fixture) in its own process with a 60 s
budget and appends one record per measurement to the JSON array in
`results/raw/node-<date>.json`. The process runs `src/measure-one.ts`,
prebundled with esbuild by `scripts/bundle-driver.mjs` into
`packages/doenetml-worker-javascript/.bench/` (rebuilt when a source is
newer), over that package's test utilities, which give the three cores one
interface (`DOENET_TEST_CORE` selects the core; the Rust and cells
adapters are `test-core-rust.ts` and `test-core-cells.ts` there).

| Field | Meaning |
|---|---|
| `status` | `ok`; `unsupported` (the adapter refused the document or an action: a gap, not a failure); `timeout` with the `stage` reached (`parse`, `load`, `errors`, `steps`, `structural`); `error`. |
| `parse_ms` | DoenetML text to normalized DAST, by `@doenet/parser` alone. |
| `load_ms` | `createTestCore` on the text: parse, core construction and the first state. Includes the parse, so `load_ms - parse_ms` is the core's own share. |
| `heap_bytes` | JS heap growth across the load after a forced GC on each side. |
| `wasm_bytes` | Wasm linear memory after the load. The JS core's figure is the Rust binding its worker holds for DAST normalization. |
| `error_components` | Error components in the loaded document, where the core can report them (`null` otherwise). A document with errors is not a valid measurement. |
| `state_bytes`, `state_gzip_bytes` | The session's saved state after the steps, raw and gzipped. The cells core's is `save_state()` JSON: one `[scope, slot, kind, value]` entry per essential cell that differs from its default (`cells-core/src/document/state.rs`). The JS core's is the `coreState` string of its persistence payload. |
| `state_envelope_bytes` | JS core only: the whole persistence payload a host stores, `coreInfo` included. |
| `steps`, `structural` | Per step label, `n` samples and `p50_ms`, `p90_ms`, `max_ms`. Steps cycle for 20 rounds or 20 s, structural steps for 10 rounds. |

Each measurement is one node process loading the bundle, about a second
of startup; that is harness overhead and appears only in `wall_ms`.

## The browser harness

```bash
npm run build -w packages/standalone -w packages/cells-viewer -w packages/doenetml-prototype
npm run build:rust-viewer
BENCH_CORES=javascript,rust,cells BENCH_FIXTURES=chain-100 npm run browser
```

`browser/perf.spec.ts` runs each fixture in each core's viewer under
headless Chromium: the JS core through the standalone bundle on
`browser/js.html`; the Rust core through the prototype viewer
(`packages/doenetml-prototype`, which renders the flat DAST the Rust core
produces) on `browser/rust-viewer/`, with `browser/rust-adapter.js`
installed; the cells core through its own viewer build with
`browser/cells-adapter.js` installed. All three pages implement one
`window.__bench` protocol (`load`, `locate`, `position`, `act`), served by
`browser/serve.mjs`. One record per (core, fixture) goes to
`results/raw/browser-<date>.json`, with a 60 s budget per fixture; the
measurements taken before the budget ran out stand, marked
`timed_out_at`.

| Field | Meaning |
|---|---|
| `load_ms` | DoenetML text to first render: for the cells viewer its own `firstRender`; for the JS core from the render call to the first frame after the core is initialized and the fixture's target (its board, or its first step's element) is in the DOM; for the Rust core from the render call to the first frame after the core's first flat DAST is in the viewer's store and the board, or the document, is in the DOM. |
| `drag` | 60 real pointer moves paced at 16 ms. `latency` is, for each frame in which the dragged point moved on screen, the time since the oldest pointer move it answers: the lag the user saw. `frames / moves` says how many of the moves got a frame of their own. For the cells core, `cells` adds the viewer's own per-tick core, commit and paint times. The prototype viewer lets JSXGraph move a dragged point before the core answers, so for the Rust core the point's position is the one the core last returned (the viewer's store), as the JS viewer moves its visible point only on the core's answer. |
| `steps`, `structural` | Steps that are not drags go through the core (`act`), each timed to the next animation frame (`frame`) and to a task after it (`paint`). |

If this machine's Playwright is newer than its installed browsers, set
`BENCH_CHROMIUM` to an installed executable (the memory benchmark reads
the same variable).

## Memory in the browser

`packages/memory-benchmark` takes `--core cells` or `--core rust` and runs the scenarios
that have an equivalent for a viewer without an embed API: `blank`,
`iframe-N` and `repeat-S`. See its README.

## Bundle size

```bash
npm run build -w packages/standalone -w packages/cells-viewer
npm run build:rust-viewer
npm run bundle
```

`src/bundle.mjs` measures everything a page fetches to render a document,
raw and brotli (quality 11, what a CDN serves precompressed), and appends
one record per set to `results/raw/bundle-<date>.json`. The sets: the JS
core's eager set (facade, eager chunk, stylesheet, worker, and the Rust
wasm the worker fetches), the whole standalone dist without maps for
context, the Rust wasm alone (it ships inside the JS core's worker), the
Rust core's page (the prototype viewer with the core worker it loads, which
carries the JS core too, since one worker serves both), and the cells
viewer build. A set whose dist is not built is skipped. The delta the cells core adds to standalone is
measured once the wiring exists.

In CI, `packages/standalone/bundle-budgets.json` now carries a
`maxBrotliBytes` ceiling beside `maxBytes` for the eager chunk, the worker
and the single-file variant, enforced by the existing size check with the
same raise-it-in-the-diff convention.

## Results

`results/RESULTS.md` opens with a one-table comparison of the three cores
("At a glance", kept by hand in `results/NOTES.md`). `npm run render`
writes `results/RESULTS.md` from the raw records, a later run superseding an
earlier one per (fixture, core) or set,
(Node, browser, memory, bundle) with `results/NOTES.md`, the hand-written
reading of them, at the top. Raw records are committed with each run.
`scripts/perf-diff.sh [base] [fixtures]` compares the cells core on a base
commit with the working tree through the Node driver, for refactors.

## Reference budgets

| Measurement | Budget |
|---|---|
| Interactive tick, browser frame latency | 16 ms |
| Structural tick, browser | 50 ms |
| Load, text to first render, `homework` | 100 ms |
| Memory, marginal per viewer on a page | 20 MB |
| State storage, `homework` after the script | 2 KB raw |
| Bundle, brotli, everything a page fetches | 1 MB |
