# Method

How the suite measures the three cores (the JS core in
`doenetml-worker-javascript`, the Rust core in `doenetml-worker-rust`, the
cells core in `cells-core`), and why it measures them this way. The
results are in `results/`; how to run the suite is in `README.md`.

## The questions

The suite answers, in order of weight:

- **Which core is faster, and by how much?** The comparison, in Node,
  core only. This is the main question, so the rest of the design serves
  it.
- **What can each core run?** The coverage, from the same run.
- **Does a core feel fast enough in a real page?** The budgets: each core
  in the browser with its own viewer, against the product budgets below.
- **Where does the time go?** In the core, the sub-measurements under
  each headline number (raw tick, floor, p90, parse, heap, wasm). From
  DoenetML text to the first render in a page, the trace layer: every
  step the cells viewer and its core take, in order, with what the
  browser does underneath (below).

Two questions belong elsewhere. Whether a change made one core slower is
`scripts/perf-diff.sh` (base against working tree, one core, nothing
committed) and each core's own benches. A one-off architecture question
gets a sweep written for it, kept with the code or ADR it answers, and
deleted afterwards.

## Runs

A run is one machine, one commit, and every core measured in one sweep,
each core built as below; fixtures and cores interleave, so a slow stretch
of the machine falls on all of them. Every page is rendered from exactly
one run and never merges runs: a ratio is only valid when both of its
sides were measured together. A newer run replaces a table whole, never
cell by cell.

Each run is committed under `results/runs/<date>-<machine>-<commit>/`
(`-dirty` when the measured code had uncommitted changes):

- `manifest.json`: the machine's id, its hardware (CPU model, cores,
  memory, OS, Node version), the commit, how each core was built, and the
  layers measured, each with its cores, fixtures and timeout.
- `node.json`, `browser.json`, `bundle.json`, `trace.json`: one array of
  records per layer, appended as measurements end.
- `comparison.md`, `coverage.md`, `budgets.md`, `trace.md` (with its
  `trace-*.svg` figures): the pages, generated by `scripts/render.mjs`,
  which also writes the index, `results/README.md`.

Any machine's run is valid. The runner names the machine (`--machine` or
`BENCH_MACHINE`); the hardware in the manifest says what the name stands
for. The index groups runs by machine, and no page compares two machines.

### Builds

Each core is measured as it would ship:

- **JS**: from source, bundled with the driver by
  `scripts/bundle-driver.mjs`.
- **Rust**: the release profile, without the logging features: `cd
packages/doenetml-worker-rust && npx wasm-pack build lib-js-wasm-binding
--target web --release`. The browser page carries the core in other
  bundles, so rebuild them after it: `npx vite build` there, then in
  `packages/doenetml-worker`, then `npm run build:rust-viewer`. The
  workspace's own build (`--dev` with logging) is several times slower,
  and any workspace build (`npm run build`, a package's `npm test`) puts
  it back, so build the Rust core last.
- **cells**: `npm run build -w packages/cells-core` (`wasm-pack --release`).

Neither core runs wasm-opt: the cells core turns it off (it corrupts
current wasm-bindgen output, `crates/cells-wasm/Cargo.toml`), and the
Rust core's release build runs it only where wasm-pack can download
binaryen. Both are the Rust compiler's release profile alone.

A runner who built a core otherwise says so in `BENCH_BUILD_<CORE>`
(`BENCH_BUILD_RUST=...`), which the manifest records.

## The shapes

The comparison runs five synthetic shapes, each exercising one mechanism, at
1,000, 10,000 and 100,000 elements: the sizes where a tick is substantial
work, and where cores differ by factors rather than percent. A document
built with `<repeat>`s reaches 100,000 components as easily as one
written out, so the largest size is not out of reach of real content.

Every shape's primary action is a drag of a point, which every core
supports, alternating between two places so every tick changes something.
How the value reaches the core (a drag, a keystroke) is a constant cost
that vanishes at these sizes; what differs is what the core does next.

| Shape       | Mechanism                                                                                                              | Runs on                                                                             |
| ----------- | ---------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `depth`     | Forward propagation through a long serial path: a dragged point feeds a chain of n numbers.                            | JS, Rust, cells                                                                     |
| `breadth`   | Forward propagation across a wide set: a dragged point feeds n independent numbers.                                    | JS, Rust, cells                                                                     |
| `inversion` | A request walked back through n operators: dragging the point at the end of a chain moves the free point at its start. | JS, cells (Rust does not invert)                                                    |
| `symbolic`  | Symbolic work: a chain of n simplified expressions in x, fed by a dragged point and evaluated at its end.              | JS, cells                                                                           |
| `rebuild`   | A structural change: the drag sets a repeat's length between n and n - 1 iterations of a number and a point.           | JS, cells (Rust has no repeat; cells caps a repeat at 10,000 iterations by default) |

The generator is `src/generate.mjs`. The text is cached in
`fixtures/generated/`, not committed.

The real documents (`fixtures/*.json`: `homework`, `lesson`, `sir`,
`venn`) are not ranked: they are for the coverage page and the budgets,
where what matters is whether a core can run them and how they feel.

## What is measured

Each (core, fixture) is a fresh Node process (`src/measure-one.ts`), so
memory figures do not carry over, through the JS worker's test adapters,
which give the three cores one interface.

- **Tick**, the headline: 3 warm-up ticks, then the median of 20. When the
  first tick takes more than 1 s, 1 warm-up and 3 samples instead. The
  headline is the median less the core's **adapter floor**: the median
  tick of the same drag on a document of one free point, measured first in
  every run. A tick within twice its floor is marked ‡: its own time is
  below what the adapter shows, so its ratio is a bound from the floor.
  Under it: the raw median, the p90, the sample count.
- **Load**: the adapter's `createTestCore` on the DoenetML text, which
  includes the parse. Under it: the parse alone.
- **Memory**: after the load, the JS heap's growth (after a forced GC on
  each side) and the core's wasm linear memory, which never shrinks. Two
  different kinds, so memory is reported in absolute terms, never as a
  ratio.

The adapters are test tools, not production paths; on the cells core they
are most of a small tick. That bias is a fraction of a millisecond per
tick, so it does not change a difference of 2× or more at these sizes,
which is what the comparison is for. The floor says how large it is.

### The value check

Every synthetic shape knows what it computes. After the samples, the
driver makes one more drag to a known place and reads the values the
shape names (the chain's two ends, the fan's first and last, the
evaluated expression, the repeat's last iteration). A core whose values
are wrong did not do the work being timed: its row says **not
comparable**, with the values it held, and shows no number. Each core is
checked against the shape, not against another core.

### Timeouts

The load has 120 s, and each tick 15 s. The load's limit is the longer
so that a core which loads slowly still has its ticks measured at 10,000:
the ticks are the headline. A core that loads but cannot finish one tick
in 15 s keeps its load. A timed-out cell shows "> 15 s" (or "> 120 s"),
and its ratio is a lower bound, "≥ N×" with N = the limit over the other
core's time, marked †: the slow side was not checked, having not finished.
A core whose load did not finish has no tick: its tick cells say so
instead of giving a bound. The stages after the ticks, which are not timed
(the value check, the saved state, the error count), have 120 s, since
reading a large document's state is slow; a timeout there costs only
their fields, and a tick whose check did not finish is marked unchecked
(†). A timeout is not retried within a run.

A core does not try a shape's larger size after a smaller one it could
not finish (a timeout, a failure, or a skip itself), or after a smaller
one whose load took more than a tenth of the load's limit, so that ten
times the size could not load in time. Its record says why it was
skipped, and its cells show no number. This keeps a run to what can
finish: without it, every size past a core's reach costs the whole load
limit.

## The pages

**Comparison**: a table per measure, tick first, then load, with every
core side by side and a row per shape and size, so a reader sees how
each core scales. The JS core's column gives its time; every other core's
column gives how many times faster or slower it is than the JS core, the
core in use today, with its own time under it. A core that cannot run a
row shows why, without hiding the others' numbers. Memory follows in the
same layout, as absolute numbers. A collapsed table at the end holds
every measurement.

**Coverage**: every fixture against every core, ✓, ✗ with the wrong
values, unsupported with the adapter's reason, or the stage that timed
out.

**Budgets**: the browser layer (`browser/perf.spec.ts`): each core in a
real page with its own viewer (the standalone viewer for JS, the prototype
viewer for Rust, the cells viewer), on the same shapes, sizes and
timeouts. A drag is 60 real pointer moves; its latency is the time from a
move to the first frame that shows the point moved. Because each viewer is
at a different stage, these numbers are read against the budgets, never
against each other. The browser has no value check of its own: a drag
whose core left wrong values in the same run's Node layer is shown as not
comparable. The browser layer is optional in a run; the manifest
says whether it ran. The bundle's size (`src/bundle.mjs`) is reported
there too.

**Trace**: the trace layer, below.

## The trace layer

The other layers each give one number for a load. The trace layer
(`browser/trace.spec.ts`) explains that number: what the cells viewer does
to get from DoenetML text to the first render, step by step and in order,
how much work each step did, and what the browser did underneath. It
measures only the cells viewer, on `homework`.

**Steps.** Every step is a User Timing measure named `cells:<path>`, so a
step nested in another is named by its path (`parse/lezerToDast`); they
also show in the Performance panel of the browser's developer tools. The
viewer records its own (`packages/cells-viewer/src/trace.ts` and its
callers): page boot, the page's first render, the editor's mount, the
document's fetch, the parse in four stages, the wasm's initialization, the
call into the core, the component table, and the render with its boards.
The core records its own spans (`cells_core::trace`, read through
`Core.load_trace_json`): deserialize, the compile's plan, check and lint,
each build's expand, resolve, loop check and emit, schedule and compute.
The viewer places them under `core/new Core`; the core's clock starts
after its bytes are copied into wasm memory, so they can sit up to that
copy late. A step carries counts of its work (characters, DAST nodes,
elements, components, cells, instructions), so its time can be read
against its size. What each step does, and where its code is, is the
glossary in `src/steps.mjs`, which the page prints; a step without an
entry is listed under the glossary so it gets one.

**The browser underneath.** One more run of each scenario is made under a
Chrome performance trace (Playwright's `browser.startTracing`). From it,
`src/chrome-trace.mjs` gives every millisecond of the page's main thread
to the innermost trace event covering it, and that event to a kind of
work: HTML, script compile, script run, wasm compile, garbage collection,
style and layout, paint, or other; what is left is idle. This is what
shows a step that took long only because the thread was busy with
something else, such as a fetch whose response waited behind a render.
Tracing slows the page (by about a fifth on the reference machine), so
the traced run's times are shown with its figures, not mixed into the
medians. Its full trace is written to `results/traces/<run>/`, ignored
by git, to open in DevTools.

**Scenarios.** Each loads the page by navigation from the viewer's build,
served as a host would serve one: content-hashed assets cached for good,
the page revalidated (`browser/serve.mjs`, port 4176). A load ends at the
first render, the end of the `render` step.

- Visits: `cold`, a new browser profile; `warm`, a second visit, with the
  files in the HTTP cache; `hot`, a third, by when Chromium has also
  cached compiled code (V8 caches a script's code on a later visit than
  its first, and wasm once it has been optimized); `edit`, the open page
  given a changed document (one paragraph more), as the editor's Refresh
  loads it.
- Pages: the editor page (`/?src=`), and the viewer alone (`?editor=0`)
  from the same bundle, which shows what mounting the editor costs.
- CPU: Chromium's throttling (`Emulation.setCPUThrottlingRate`), ×1 and
  ×4, standing in for a slower device; the network is not slowed.
- Size: `homework-x<n>` repeats the homework page in `n` sections
  (`src/trace-fixtures.mjs`), on the editor page. A step whose time stays
  put as `n` grows is a fixed cost of the page; one that grows with `n` is
  work on the document.

Each scenario runs `BENCH_TRACE_RUNS` times (5 by default), each in a new
browser profile so `cold` is always cold; a step's time on the page is its
median, and a step that runs more than once in a load (a board per graph,
a build pass) is matched by its occurrence.

## Budgets

Product goals, not gates (the only gate is CI's bundle size check,
`packages/standalone/bundle-budgets.json`).

| Measurement                                     | Budget                              |
| ----------------------------------------------- | ----------------------------------- |
| Frame latency of a drag, browser                | 16 ms (one vsync)                   |
| Frame latency of a drag that rebuilds, browser  | 50 ms                               |
| Load, text to first render, `homework`          | 100 ms: no loading screen           |
| State storage, `homework` after its script, raw | 2 KB                                |
| Bundle, brotli, everything a page fetches       | 1 MB                                |
| Memory, marginal per viewer on a page           | 20 MB (`packages/memory-benchmark`) |
